# Стиль коду

> [English](../../CODING_STYLE.md) | [中文](../zh-CN/CODING_STYLE.md) | [Français](../fr-FR/CODING_STYLE.md) | [Español](../es-ES/CODING_STYLE.md) | [日本語](../ja-JP/CODING_STYLE.md) | [العربية](../ar-MA/CODING_STYLE.md) | **Українська**

Ця стаття описує загальні правила стилю коду, які слід використовувати для нового коду LiberNT. Ці правила застосовуються виключно до вихідних файлів C та C++. Вони походять зі стилю коду ReactOS, який учасники ReactOS узгодили на своїй зустрічі в жовтні 2013 року.

Наявний код не перетворюється на цей стиль у межах не пов'язаних змін. Див. [Зауваження щодо переформатування наявного коду](#зауваження-щодо-переформатування-наявного-коду) для детальнішої інформації.

Код, синхронізований з іншими джерелами (як-от Wine), не повинен переписуватися. Файли [3rd Party Files.txt](../../media/doc/3rd%20Party%20Files.txt) та [WINESYNC.txt](../../media/doc/WINESYNC.txt) можна використовувати для відстеження синхронізованих файлів.

## Структура файлів

1. Кожен новий файл вихідного коду LiberNT повинен містити заголовок файлу такого вигляду:

```
/*
 * PROJECT:     LiberNT Kernel
 * LICENSE:     GPL-3.0-or-later (https://spdx.org/licenses/GPL-3.0-or-later)
 * PURPOSE:     Does cool things like Memory Management
 * COPYRIGHT:   Copyright 2017 Arno Nymous <abc@mailaddress.com>
 *              Copyright 2017 Mike Blablabla <mike@blabla.com>
 */
```

Будь ласка, використовуйте ідентифікатори ліцензій SPDX, доступні на https://spdx.org/licenses.
Це робить наш вихідний файл придатним для розбору інструментами перевірки ліцензій!

Вам слід додати себе до розділу `COPYRIGHT` файлу, якщо ви зробили в нього значний внесок і можете взяти на себе відповідальність за весь файл або його частину. У цьому списку для кожного файлу має бути не більше ніж 3 особи. Ніколи не видаляйте й не змінюйте рядки авторського права та ліцензії, які вже присутні у файлі.

Рядок `FILE` старого заголовка слід вилучити.

2. Для кодової бази LiberNT використовується генератор документації [Doxygen](https://www.doxygen.nl/) з файлом `Doxyfile` у кореневому каталозі, тому використовуйте належний заголовок для функцій; див. [API Documentation](https://reactos.org/wiki/Documentation_Guidelines#API_Documentation) у вікі ReactOS для деталей.

## Відступи та ширина рядка

1. Ширина рядка має бути не більше ніж **200 символів**.
2. Не додавайте пробіл або табуляцію в кінці будь-якого рядка.
3. Робіть відступи за допомогою **4 пробілів**, не використовуйте табуляцію!
4. Робіть відступ як для мітки case, так і для інструкції case всередині оператора switch.

**Правильно:**
```c
switch (Condition)
{
    case 1:
        DoSomething();
        break;

    case 2:
    {
        DoMany();
        ManyMore();
        OtherThings();
        break;
    }
}
```

**Неправильно:**
```c
switch(Condition)
{
case 1:
     DoSomething();
     break;
case 2:
    DoMany();
    ManyMore();
    OtherThings();
    break;
}
```

5. Якщо виклик функції не вміщується в один рядок, вирівнюйте аргументи так:
```c
FunctionCall(arg1,
             arg2,
             arg3);
```

6. Заголовки функцій повинні мати такий формат (зі збереженням порядку, як у прикладі):
```c
static    // ідентифікатор видимості
CODE_SEG("PAGE")    // розміщення в секції
// інші атрибути
BOOLEAN    // тип повернення
FASTCALL    // конвенція виклику
IsOdd(
    _In_ UINT32 Number);
```

## Пробіли

1. Не використовуйте пробіли навколо унарних операторів.  
**Правильно:** `i++;`  
**Неправильно:** `i ++;`

2. Ставте пробіли навколо бінарних і тернарних операторів.  
**Правильно:** `a = b + c;`  
**Неправильно:** `a=b+c;`

3. Не ставте пробіли перед комою та крапкою з комою.

**Правильно:**
```c
for (int i = 0; i < 5; i++)
    DoSomething();

func1(a, b);
```

**Неправильно:**
```c
for (int i = 0; i < 5 ; i++)
    DoSomething();

func1(a , b) ;
```

4. Ставте пробіли між керуючими операторами та їхніми круглими дужками.

**Правильно:**
```c
if (Condition)
    DoSomething();
```

**Неправильно:**
```c
if(Condition)
    DoSomething();
```

5. Не ставте пробіли між назвою функції та її дужками або між дужкою та її вмістом.

**Правильно:**
```c
func(a, b);
```

**Неправильно:**
```c
func (a, b);
func( a, b );
```

## Перенесення рядків

1. Кожна інструкція повинна займати власний рядок.

**Правильно:**
```c
x++;
y++;

if (Condition)
    DoSomething();
```

**Неправильно:**
```c
x++; y++;

if (Condition) DoSomething();
```

## Фігурні дужки

1. Завжди розміщуйте фігурні дужки (`{` та `}`) на окремих рядках.
2. Однорядкові керуючі блоки можуть містити фігурні дужки, але це не обов'язково. Винятком є однорядкові керуючі блоки з додатковими коментарями.

**Правильно:**
```c
if (Condition)
    DoSomething();

if (Condition)
{
    DoSomething();
}

if (Condition)
{
    // This is a comment
    DoSomething();
}

if (A_Very || (Very && Long || Condition) &&
    On_Many && Lines)
{
    DoSomething();
}

if (Condition)
    DoSomething();
else
    DoSomethingElse();

if (Condition)
{
    DoSomething();
}
else
{
    DoSomethingElse();
    YetAnother();
}
```

**Неправильно:**
```c
if (Condition) {
    DoSomething();
}

if (Condition)
    // This is a comment
    DoSomething();

if (A_Very || (Very && Long || Condition) &&
    On_Many && Lines)
    DoSomething();

if (Condition)
    DoSomething();
else {
    DoSomethingElse();
    YetAnother();
}
```

## Керуючі структури

1. Не використовуйте інверсну логіку в умовах керуючих операторів.  
**Правильно:** `if (i == 1)`  
**Неправильно:** `if (1 == i)`

2. Уникайте занадто багатьох рівнів вкладених керуючих структур. Віддавайте перевагу «лінійному стилю» перед «деревоподібним». Використовуйте `goto`, коли це допомагає зробити код чистішим (наприклад, для шляхів очищення ресурсів).

**Правильно:**
```c
if (!func1())
    return;

i = func2();
if (i == 0)
    return;

j = func3();
if (j == 1)
    return;
...
```

**Неправильно:**
```c
if (func1())
{
    i = func2();
    if (func2())
    {
        j = func3();
        if (func3())
        {
            ...
        }
    }
}
```

## Іменування

1. Пишіть назви змінних та функцій з великої літери (PascalCase). При розробці під Win32 можна використовувати угорську нотацію, але це не вимагається. Якщо ви її не використовуєте, перша літера назви все одно має бути великою (ніякого lowerCamelCase). Також не використовуйте підкреслення як роздільники слів.

**Правильно:**
```c
PLIST_ENTRY FirstEntry;
VOID NTAPI IopDeleteIoCompletion(PVOID ObjectBody);
PWSTR pwszTest;
```

**Неправильно:**
```c
PLIST_ENTRY first_entry;
VOID NTAPI iop_delete_io_completion(PVOID objectBody);
PWSTR pwsztest;
```

2. Уникайте скорочень у назвах функцій і змінних, використовуйте описові дієслова, де це можливо.

3. Перед булевими значеннями вказуйте змістовні префікси, такі як "Is" або "Did", якщо це можливо і підходить за контекстом.

**Правильно:**
```c
BOOLEAN IsValid;
BOOLEAN DidSendData;
```

**Неправильно:**
```c
BOOLEAN Valid;
BOOLEAN SentData;
```

## Коментарі

1. Уникайте марнотратних коментарів, які могли б вміститися в один рядок.

**Правильно:**
```c
// This is a one-line comment

/* This is a C-style comment */

// This is a comment over multiple lines.
// We don't define any strict rules for it.
```

**Неправильно:**
```c
//
// This comment wastes two lines
//
```

## Null, false та 0

1. Нульовий вказівник слід записувати як `NULL`. У рідкісних випадках, коли ваше середовище рекомендує інший нульовий вказівник (наприклад, C++11 `nullptr`), ви, звісно, можете його використовувати. Лише не використовуйте значення `0`.

2. Булеві значення Win32/NT слід записувати як `TRUE` та `FALSE`. У тих окремих випадках, коли ви використовуєте змінні `bool` у C/C++, записуйте їх як `true` та `false`.

3. Коли потрібно завершити рядок ANSI або OEM чи перевірити його термінатор, використовуйте `ANSI_NULL`. Якщо рядок Unicode або широких символів, використовуйте `UNICODE_NULL`.

## Зауваження щодо переформатування наявного коду

- Ніколи повністю не переформатовуйте файл одночасно зі зміною коду в ньому. Робіть це в окремих комітах.
- Якщо коміт містить лише зміни форматування, чітко зазначте це в повідомленні коміту, додавши префікс *[FORMATTING]*.

## Інші моменти

- Не використовуйте `LARGE_INTEGER`/`ULARGE_INTEGER`, якщо це не потрібно для виклику API. Замість них використовуйте `INT64`/`UINT64`
- Використовуйте `#pragma once` замість захисних макросів `#define` у заголовних файлах
- Не вказуйте конвенцію виклику для функції, якщо це не обов'язково (зазвичай це потрібно для API або експортованих символів)

## Використання автоматичного інструменту форматування коду

Файл `.clang-format` у кореневому каталозі описує цей стиль для clang-format. Використовуйте його лише для нового коду, дотримуючись вищезгаданих правил щодо переформатування наявного коду.
