# Правила керування Pull Request'ами

> [English](../../PULL_REQUEST_MANAGEMENT.md) | [中文](../zh-CN/PULL_REQUEST_MANAGEMENT.md) | [Français](../fr-FR/PULL_REQUEST_MANAGEMENT.md) | [Español](../es-ES/PULL_REQUEST_MANAGEMENT.md) | [日本語](../ja-JP/PULL_REQUEST_MANAGEMENT.md) | [العربية](../ar-MA/PULL_REQUEST_MANAGEMENT.md) | **Українська**

Щоб підтримувати прийнятну кількість відкритих, але неактивних PR, слід враховувати такі правила:
- Якщо PR має щонайменше одне схвалення, його можна злити після 1 тижня очікування додаткових коментарів.
  - Якщо зміна має щонайменше 3 схвалення або ви вважаєте її достатньо простою, її можна злити одразу.
- Якщо PR занадто довго перебуває у стані "changes requested" і від автора немає ознак роботи над ним, його слід закрити.
  - Загальне правило: 2 тижні для невеликого PR. Для великого PR термін може бути довшим.
  - PR можна відкрити знову будь-коли, якщо у вас з'явилися додаткові коментарі або було внесено нові зміни.
- Якщо вам потрібне рецензування від певної особи, призначте PR цій людині. Не покладайтеся лише на функцію GitHub "review requested".
- Пам'ятайте про мітки (labels) для PR. Ви можете призначити відповідну мітку пулл-реквесту, щоб позначити його область дії, привернути додаткову увагу чи просто для зручнішої навігації.
- Не вважайте себе зобов'язаними коментувати все, що бачите, лише заради коментування. Чи то на GitHub, чи в Discord або Matrix.

Крім того, щоб не здатися грубими щодо доброзичливих авторів внесків, будь ласка, утримуйтеся від:
- Прохання до автора виконати не пов'язану із завданням роботу
- Закриття PR без пояснення причини
- Злиття з наміром переписати цей код невдовзі після цього

Перед злиттям PR переконайтеся, що він відповідає [правилам участі у проєкті](CONTRIBUTING.md#правила-та-рекомендації), але що важливіше:
- Переконайтеся, що автор вказав справжню адресу електронної пошти в усіх комітах PR
- Якщо PR містить код або переклади, переконайтеся, що автор вказав не нікнейм або псевдонім, а повне офіційне ім'я (legal name) в усіх комітах PR
- Якщо PR містить медіафайли (шпалери, теми, іконки, звуки) або документацію поза кодом, переконайтеся, що автор вказав ім'я або псевдонім в усіх комітах PR
- Якщо PR містить змішані зміни коду та медіафайлів, розглядайте його як PR з кодом
- Важливі примітки перед використанням стратегії "Squash and merge" для PR:
  - Переконайтеся, що ім'я автора в профілі GitHub збігається з іменем у комітах. Якщо це не так, попросіть автора налаштувати його відповідним чином.
  - Якщо автор не бажає вказувати ім'я в профілі GitHub:
    - До PR необхідно додати мітку "no squash merge".
	- Переконайтеся, що кожне повідомлення коміту оформлено правильно відповідно до [.gitmessage](../../.gitmessage).
	- Зрештою, у такому разі PR має бути злитий або за допомогою стратегії "Rebase and merge", або вручну.
  - Натискаючи кнопку "Squash and merge" в PR, ви можете переконатися, що автор не використовує адресу no-reply —
  під повідомленням коміту з'явиться напис: `This commit will be authored by <address@email.com>`
