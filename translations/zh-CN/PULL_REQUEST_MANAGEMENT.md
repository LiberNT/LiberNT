# Pull Request 管理规则

> [English](../../PULL_REQUEST_MANAGEMENT.md) | **中文**
>
> 翻译说明：本译文由 AI 初译并排版；术语、代码块、链接与锚点已与英文原版核对，中文术语已经人工核对。如有纰漏，请提交 issue 指出；表述以英文版为准。

为了把长期无人处理的开放 PR 控制在可接受的范围内，请遵循以下规则：

- PR 至少获得一个批准后，再等 1 周收集其他意见即可合并。
  - 如果已有至少 3 个批准，或你认为改动足够琐碎，可以直接合并。
- PR 长时间停留在 "changes requested" 状态，且作者没有表示会继续处理，应当关闭。
  - 经验值：小型 PR 等 2 周；大型 PR 可以更久。
  - 之后随时可以重新打开，前提是有新的意见或新的改动。
- 如果需要某个人审查，直接把 PR 指派给他，不要只依赖 GitHub 的 "review requested" 功能。
- 别忘了 PR 标签。给 PR 打上合适的标签，可以标明范围、吸引注意，也方便检索。
- 不必为了留言而留言，无论是在 GitHub、Discord 还是 Matrix 上。

另外，为了避免让热心的贡献者觉得被冒犯，请避免：

- 要求贡献者做无关的工作
- 不说明理由就关闭
- 刚合并就打算重写那段代码

合并 PR 之前，确认它符合[贡献规则](CONTRIBUTING.md#规则与建议)，更重要的是：

- 确认作者在所有 PR 提交里都填了真实邮箱
- PR 含代码或翻译时，确认作者在所有提交里用的是完整法定姓名，而不是昵称或别名
- PR 只含媒体(壁纸、主题、图标、声音)或代码之外的文档时，确认作者在所有提交里填了姓名或别名
- PR 同时含代码和媒体改动时，按含代码的 PR 处理
- 对 PR 使用 "Squash and merge" 之前注意：
  - 确认 GitHub 资料里的姓名与提交中的一致。不一致就请作者改。
  - 如果作者不愿改 GitHub 资料里的姓名：
    - 给 PR 加上 "no squash merge" 标签。
    - 确认每条提交信息都按 [.gitmessage](../../.gitmessage) 的格式书写。
    - 这种情况下，PR 需要用 "Rebase and merge" 或手工合并。
  - 在 PR 里点 "Squash and merge" 时，可以确认作者没有使用 no-reply 邮箱 —— 提交信息下方会显示：`This commit will be authored by <address@email.com>`
